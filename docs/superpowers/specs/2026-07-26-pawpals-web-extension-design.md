# PawPals 网页 + 浏览器插件形态设计

日期：2026-07-26

## 背景

PawPals 目前是 Electron 桌面应用。前端是标准 React + Vite，通过 HTTP 和 Socket.IO 与本地 Express 服务通信；Electron 主进程只做两件事：开一个窗口 `loadURL` 到本地服务（`electron/main.mjs:302`），以及轮询任务队列、用 Playwright 执行 Boss 直聘的登录、搜岗、投递。

也就是说，产品主体本来就是一个网页，Electron 是外壳加自动化手臂。

自动化目前是写死选择器的脚本流程（`electron/platforms/boss-playwright.mjs`）。Boss 直聘改版一次，投递流程即失效。

## 目标

把产品形态改为**网页 + 浏览器插件**：

- 网页承担群聊主界面、多 Agent 编排、数据存储
- 插件承担页内悬浮宠物、以及 computer use 形式的浏览器自动化
- Electron 在能力迁移完成后下线

## 范围

**本次做：**

1. 浏览器插件骨架：悬浮宠物、侧边栏群聊入口、与服务端通信
2. computer use 执行层：感知 → 决策 → 执行 循环，替换写死选择器
3. 自动化能力从 Electron 迁移到插件：登录、搜岗、投递

**本次不做：**

- 多租户与账号体系
- 云端部署
- 真正的桌面宠物（脱离浏览器、常驻 macOS 桌面）
- 支付与计费

由于不做云端部署，插件侧边栏加载的群聊页面与服务端接口均指向本机运行的服务（默认 `http://localhost:3010`）。这意味着插件只在本机服务运行时可用，不具备分发给他人直接使用的条件。这是本次有意接受的限制：先把形态与能力跑通，部署作为后续独立工作。

## 关键决策

### 采用网页 + 插件，而非增强 Electron

考虑过三种形态：

| 形态 | 结论 |
|---|---|
| 沙盒招聘站 + 服务端 Playwright | 否决。能力真实但目标站是自建的，不解决真实平台的使用需求 |
| Electron 桌面宠物 + computer use | 否决。能力最强且无 `isTrusted` 顾虑，但安装摩擦大，且与「做成网站」的诉求相反 |
| **网页 + 插件** | **采用。** 网页部分已经存在；插件安装摩擦远低于 dmg；宠物与自动化合于一处，无需两端状态同步 |

采用插件的额外收益：用户浏览岗位页时，JD 就在当前 DOM 里，可直接读取。现有实现需要用户复制链接、再由 `fetchJdContent`（`server.ts:2267`）经 Electron BrowserWindow 绕回去抓取，这段可以删除。

### 执行层设计为可替换适配器

computer use 分三步，只有第三步受浏览器事件真实性影响：

- **感知**：读 DOM 抽取可交互元素 —— 与事件真实性无关
- **决策**：LLM 选择元素与动作，跑在服务端 —— 与浏览器无关
- **执行**：真正点下去 —— 受影响

Playwright 经 CDP 发出 `isTrusted: true` 的事件；插件 content script 只能发 `isTrusted: false` 的合成事件。Boss 直聘是否因此拒绝操作，**目前未经验证**——这个判断此前只是 `human-behavior.mjs` 注释中的设计假设。

因此执行层定义为接口，提供两套实现：

- `act/synthetic.js` —— 合成事件实现
- `act/debugger.js` —— `chrome.debugger` 经 CDP 发真事件实现，代价是浏览器顶部常驻调试提示条，且该权限基本无法通过 Chrome 应用商店审核

选用哪套由验证实验（见「未决事项」）的结果决定，其余设计不受影响。

### 采用 DOM 索引而非截图定位

感知层把页面可交互元素抽成带编号的列表交给 LLM，由 LLM 返回编号加动作，而不是给 LLM 截图让它返回坐标。

理由：视觉方案每步消耗视觉 token，成本高且慢；DOM 方案便宜一个数量级、不会点偏，且招聘网站均为常规 DOM 结构。代价是纯 canvas 页面无法处理，这不影响目标场景。

### 侧边栏采用 chrome.sidePanel

content script 注入的浮层在每次页面导航时被销毁，聊天面板会随之清空。`chrome.sidePanel` 跨导航保持存在。

## 架构

```
┌─ 浏览器插件 ────────────────────────────────┐
│  页内悬浮宠物（content script）              │
│  侧边栏群聊（chrome.sidePanel + iframe）      │
│  感知层：DOM → 带编号元素列表                 │
│  执行层：适配器接口                           │
│    ├─ 合成事件实现                            │
│    └─ chrome.debugger 实现                    │
└──────────────┬──────────────────────────────┘
               ↕ HTTPS + WebSocket
┌──────────────┴──────────────────────────────┐
│  server.ts（现有编排层，不改动）               │
│    多 Agent 路由 · AGENT_TOOLS 工具白名单     │
│  + server/computer-use/（新增）               │
│      决策循环 · 护栏 policy · prompt 渲染      │
└─────────────────────────────────────────────┘
```

多 Agent 编排层保持原样。改变的是「手怎么动」，不是「谁来决定动」。

## 组件划分

新代码全部走新目录。`server.ts`（5458 行）与 `src/App.tsx`（5010 行，其中 `App()` 单个组件占 4300 行）已过大，不再向其中添加内容。

**插件代码位于现有仓库下的新目录 `extension/`**（不另建仓库，以共用构建工具与提交历史）：

| 路径 | 职责 |
|---|---|
| `background/service-worker.js` | 与服务端长连接、任务分发、会话生命周期 |
| `content/pet.js` | 悬浮宠物注入与交互 |
| `perceive/` | DOM → 带编号可交互元素列表；可见性与可点击性判定 |
| `act/adapter.js` | 执行层接口定义 |
| `act/synthetic.js` | 合成事件实现 |
| `act/debugger.js` | `chrome.debugger` 实现 |
| `act/human.js` | 拟人化操作节奏，自 `electron/platforms/human-behavior.mjs` 移植 |
| `sidepanel/panel.html` | iframe 壳，加载群聊页面 |

**服务端新增 `server/computer-use/`：**

| 文件 | 职责 |
|---|---|
| `loop.ts` | 感知 → 决策 → 执行 循环，步数上限与终止条件 |
| `policy.ts` | 护栏判定，纯函数 |
| `prompt.ts` | 元素列表渲染为 LLM 可读格式 |

`perceive`、`policy`、`prompt` 均为纯函数，可离线测试。

## 数据流

一次自动投递：

1. 用户在群聊中要求投递某岗位
2. `server.ts` 现有路由将消息交给 `app-tracker`
3. `app-tracker` 调用 `apply_job` 工具（该工具已在 `AGENT_TOOLS` 中授权给它，且属于 `CONFIRM_REQUIRED_TOOLS`）
4. `apply_job` 的语义变更：不再直接执行投递，而是**开启一个 computer use 会话**
5. 循环执行：
   - 插件打开岗位页，回报感知结果（元素列表、页面标题、URL）
   - `prompt.ts` 渲染为 LLM 输入，附带本次会话目标
   - LLM 返回单步动作，形如 `{action, index, reason}`
   - `policy.ts` 校验，通过才下发插件
   - 插件执行，回报新的感知结果
   - 重复，直至 LLM 判定完成、超出步数上限、policy 拒绝、或超时
6. 结果如实回报给 agent，写入协作表

## 护栏

失败模式随架构改变：写死选择器的失败是「点不到并报错」，噪声大但安全；LLM 自主操作的失败是「点到了别的东西并认为自己成功了」，安静但危险。

| 护栏 | 内容 |
|---|---|
| 域名白名单 | 仅允许在已声明的招聘站执行动作；LLM 要求导航至其他域名一律拒绝 |
| 动作黑名单 | 永不允许删除、支付、修改账号设置；文案含「注销 / 解绑 / 删除 / 支付」的元素不予点击 |
| 需确认动作 | 所有「发送」类动作（向 HR 发消息、提交申请）首次执行前必须由用户确认，复用现有 `CONFIRM_REQUIRED_TOOLS` 机制 |
| 步数上限 | 单次会话上限 15 步，超出即终止并如实回报 |
| 验证码即停 | 感知层识别到验证码或频率限制提示，立即停止并将控制权交还用户。不尝试绕过验证码 |
| 全程留痕 | 每步的感知摘要、LLM 决策、policy 判定、执行结果写入 JSONL |

**成功判定必须是确定性的。** 投递是否成功由确定性检查决定——投递后在 Boss 的沟通列表中确认该条消息确实存在——而不是由 LLM 自述。此前 `app-tracker` 出现过未实际投递却汇报完成的情况，修复方式是让它从协作表读取真实 URL 而非由 LLM 生成；此处沿用同一思路。

## 错误处理

| 失败 | 处理 |
|---|---|
| 插件断连 | MV3 service worker 空闲约 30 秒后休眠，长会话必然中断。会话状态存于服务端而非插件，重连后按 sessionId 续接；保活使用 `chrome.alarms` |
| 导航后 content script 丢失 | 每次导航重新注入。每步执行前先握手确认脚本就绪，不盲发指令 |
| LLM 返回不合法动作 | 属常规路径而非异常路径。schema 校验失败则将错误回喂 LLM 重试，最多 2 次；仍失败则终止会话并如实回报，不静默跳过 |
| 元素编号失效 | 页面可能在感知与执行之间变化。感知时为每个元素记录指纹（标签、文案、位置），执行前校验一致性，不一致则重新感知。缺少此项会导致点击错误元素 |
| 验证码 / 风控 | 立即停止，控制权交还用户 |
| 超时 | 单步超时与整会话超时两级 |

## 测试策略

| 层 | 测什么 | 方式 |
|---|---|---|
| 单元 | perceive / policy / prompt | 纯函数。保存真实 Boss 页面 HTML 快照作为 fixture，离线运行，不联网不消耗 token |
| 集成 | act 两套适配器 | 自建本地测试页面，含 React 受控组件与各类按钮，两套实现均需通过。同时将事件真实性的结论固化为回归测试 |
| 端到端 | 决策循环 | 接入现有 `evals/` 框架，新增 `computer-use` suite：给定页面快照序列与目标，评判 LLM 决策是否合理 |

现有 routing suite 的 100% 准确率是结构性必然——`evals/judges/routing-judge.ts` 复刻的是 `detectTargetAgent` 的字符串匹配逻辑，不经过 LLM，且 30 条 case 中 22 条的期望值即为默认兜底。computer-use suite 的 case 具备天然难度梯度（按钮文案变化、按钮被弹窗遮挡、页面存在多个相似按钮），其分数具有信息量。

**明确不测**：真实 Boss 上的端到端投递无法自动化测试，因为会真实发送消息给 HR。此部分只能手动验证，每次验证均有成本。因此 fixture 库需持续积累——每次手动验证遇到的新页面形态都应保存快照。

## 迁移路径

Electron 目前独占 Boss 登录、搜岗、投递三项能力（`electron/platforms/boss-playwright.mjs`、`boss.mjs`、`web-form.mjs`）。在插件承接全部三项之前不能删除。顺序：

1. 插件骨架：宠物、侧边栏、与服务端通信
2. 感知层
3. 执行层（实现选型取决于验证实验结果）
4. 迁移登录
5. 迁移搜岗
6. 迁移投递
7. 三项均在插件中跑通后，Electron 下线

## 未决事项

**事件真实性验证**。验证插件已就位于 `~/Downloads/pawpals-spike-extension/`，为 MV3 未打包扩展，仅操作 Boss 搜索框并恢复原值，不产生任何账号写入。运行后按结果分支：

- 合成事件可驱动页面 → 采用 `act/synthetic.js`，保留应用商店上架可能
- 合成事件无法驱动页面 → 采用 `act/debugger.js`，接受常驻调试提示条与自行分发

在结果产出前，除执行层实现选型外的所有设计均可推进。

**LLM API Key 处理**。`llm.ts` 中的 Gemini key 为硬编码明文，且 `llm.ts` 未纳入版本控制。插件形态下前端与服务端的边界发生变化，需要确认 key 的存放与调用路径。
