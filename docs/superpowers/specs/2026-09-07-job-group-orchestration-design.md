# 求职群多 Agent 编排改造设计

日期：2026-09-07
状态：已评审通过，待拆实施计划

## 背景

求职群里挂着 7 个 agent，但「多 agent 协作」在服务端基本没有真正发生。盘点出七条问题，
按严重程度排列：

1. **多专家协作几乎从不触发。** 触发门槛是一条正则（`server.ts:3271`）：一句话里必须同时
   出现两个领域的词才会去调 `orchestrate()`。「帮我看看这个岗我合不合适」不触发。日常使用中
   看到的几乎全是单 agent，多专家那段代码大部分时间是死的。

2. **触发了也只是并发，不是协作。** `Promise.all`（`server.ts:3290`）里每个专家拿到的都是
   同一份背景（最近 6 条对话、每条截 300 字）加档案简历。专家之间互相看不见——简历专家不知道
   岗位猎手搜到了什么，猎手也不知道简历长什么样。

3. **综合被 prompt 主动禁止。** 汇总步骤的 prompt 原文：「你只需要用 1-2 句话做简短收尾……
   绝对不要重复专家的内容」（`server.ts:3311`）。用户看到 N 段互不相干的长文加一句「搞定啦」。

4. **首席接话时手里是空的（bug）。** 单专家路径下专家回完，首席无条件再接一段
   （`server.ts:3396`），但那次调用传的 messages 只有一句
   `"${agent.name} 刚刚完成了任务。请接住结果、总结给用户、推进下一步。"`——没有对话历史，
   也没有专家刚产出的内容。被要求「接住结果」而结果没递给它，只能说空话。

5. **专家没有记忆。** 每个专家收到的是伪造的单轮消息 `[{role:"user", content:"【来自团团的任务】…"}]`，
   同一专家第二次被调用时不记得自己上一轮说过什么。

6. **接力靠正则抓文本。** `detectMentionedAgents`（`server.ts:3354`）从回复里 match `@名字` 和
   `sessions_spawn`。模型顺口写一句「可以问问 @简历专家」就会触发一次完整调用；想交接却没写对
   格式则不会发生。交接是否发生取决于模型措辞。

7. **前端只有一个「正在思考」槽位。** `App.tsx:940` 的 `setAgentThinking` 是单值，`agent_done`
   无条件清空。并行时多个专家同时 thinking，界面只显示最后一个，任一先完成指示器就整个消失。

1–4 是「协作没发生」，7 是「发生了也看不见」，5、6 是让它不稳定的底噪。

根因是**三条各自独立的代码路径**（并行多专家 / 路由到单专家 / 首席直接回加正则接力），各自拼
上下文、拼法都不同。第 4 条 bug 就是这种不一致的产物。

### 范围外但已记录的发现

- **考公群和考研群没有 AI。** 服务端只有 `else if (msg.groupId === "job")` 接了 agent
  （`server.ts:4711`），另外两个群走最后的 `else`，从写死的语料里随机抽一句（`server.ts:4337`，
  每个「成员」两句话）。前端 `CIVIL_AGENTS` / `GRAD_AGENTS` 各定义 5 个成员，服务端一个都不存在。
  本轮不处理——先把通用编排在求职群跑通，那两个群下一轮接入时主要是配人设与工具白名单。
- **路由做了两遍。** 消息进来先过 `detectTargetAgent`（`server.ts:4745`），进 `runAgentChain`
  后又过 `resolveRoute`（`server.ts:3321`），两者的 @ 匹配正则还不完全一致。本设计在新入口内收口。

## 方案选型

考虑过三条路：

- **原地修四处**——改动小，但三条路径仍是三条，拼上下文仍是三份，下次还会长出第四条。
- **黑板 + 每轮由首席判断下一步**——协作能力最强，但每轮一次判断调用，对用户自付 API Key 的
  产品成本太重。
- **共享工作记录 + 一次性计划 + 综合**（采纳）——信息共享拿满（追加一份记录并拼进 prompt，
  不产生额外模型调用），调度只花一次。

选型过程中澄清过一点：**信息共享与调度是两个正交维度**。黑板只解决信息共享，不决定「谁接着上」。
「每轮判断」贵在调度，不在黑板。因此采纳方案取黑板的全共享 + 一次性计划的低成本调度。

## 设计

### 共享工作记录

一次用户提问 = 一个 turn。turn 内维护 `TurnLog`，每个专家跑完追加一条：

```ts
type TurnEntry = {
  agentId: string;
  agentName: string;
  task: string;
  reply: string;
};
```

**所有 agent 的 prompt 由同一个函数拼装**，固定四块：

1. 真实对话历史（取代现在「最近 6 条各截 300 字」的摘要）
2. 用户档案 + 简历（沿用现有 `sharedProfileCtx` 的读取方式）
3. **本轮其他伙伴已经做了什么**（TurnLog）— 新增，是「协作」二字唯一的落点
4. 你的任务

这一处收口取代现存的三份拼法，第 4 条 bug 随之消失。

### 出计划

首席一次 LLM 调用，返回 `PlanTask[]`：

```ts
type PlanTask = { agentId: string; task: string; dependsOn?: string[] };
```

- 空数组 = 不需要专家，首席自己答
- 一个任务 = 单专家，走同一套流程（不再是独立代码路径）
- 多个任务 = 按 `dependsOn` 拓扑分批，同批并行，批间串行

`dependsOn` 以 agentId 引用；同一 agent 一轮内只出现一次。

**兜底**：解析失败、未知 agentId、依赖成环——一律降级为空计划（首席自己答），不抛错。

**省钱通道**：用户显式 `@某人` 或「回复 某人：」时跳过出计划调用，直接构造单任务计划。

### 执行

按拓扑批次执行。同批 `Promise.all` 并行，批与批之间串行；每批结束后把产出写入 TurnLog，
下一批的 prompt 因此看得见前面所有批次的产出。

### 综合

首席拿**完整对话历史 + 完整 TurnLog** 做一次真正的综合。prompt 职责从「1-2 句收尾且绝对不要
重复专家内容」改为：**指出各家产出之间的关联和冲突、给出下一步**，引用但不复述。

已知张力：专家的长文已各自流式发到群里，首席再来一段容易啰嗦。彻底的解法是专家产出不单独成条、
只由首席汇总输出，但那要改 `streamAgent` 的呈现方式，属于体验层，本轮不动。本轮的综合比现状
实质得多，但不是终态。

**追加轮**：综合时首席可输出「还差一步」及要追加的任务，**最多触发一次**（硬上限），是黑板模型
纠错能力的低成本替代。

**专家回复里的 @ 不再直接触发调用**。改为收集起来，作为首席判断是否需要追加轮的输入信号。
交接由计划决定，不由模型措辞决定。

### 接入点与新旧并存

`runAgentChain` 有 11 个调用点。本轮**只接管一个**：用户在求职群正常发消息那条分支
（`server.ts:4745` 所在的 else）。`@all`、onboarding、四个 workflow、Boss 登录后续均保持原样
走旧路径。

代价是新旧两套编排并存一段时间。取此代价的理由：一次性换掉 11 个调用点，出问题时无法定位是
哪一处坏的。

被新入口绕开的旧逻辑——正则门槛 `needsMultiAgent`、`orchestrate()`、`resolveRoute` 分支、
无上下文的首席收尾、正则接力——**不删除**，其它入口仍在使用。

### 前端指示器

`agentThinking` 由单值改为集合：`agent_thinking` 加入，`agent_done` 按 agentName 移除。
需要服务端 `agent_done` 一并带上 agentName。

不改的话，并行成为常态后这轮改进在界面上会呈现为「闪来闪去然后消失」。

## 模块边界与测试

新建 `server/orchestration.ts` 放纯函数，`server.ts` 只留 IO 调用——照 `server/routing.ts` 的先例。

| 函数 | 职责 | 关键断言 |
|---|---|---|
| `parsePlan(raw, validAgentIds)` | 解析首席输出的计划 | 非法 JSON、未知 agentId、依赖成环均降级为空计划 |
| `batchByDependency(tasks)` | 拓扑分批 | 无依赖同批；有依赖分批；环被拒 |
| `buildAgentPrompt({history, profile, turnLog, task})` | 统一拼装 | **TurnLog 确实拼进了 prompt** —— 整个方案成立与否的断言 |
| `parseNeedMore(reply)` | 解析追加轮信号 | 无信号、格式错误均返回空 |

配套 `server/orchestration.test.ts`。

## 验收

- 「帮我看看这个岗我合不合适」这类不含双领域关键词的提问，能按需触发多专家（现状：永不触发）
- 后跑的专家 prompt 里含有先跑完专家的产出（现状：互相看不见）
- 首席综合时 prompt 内含专家产出与对话历史（现状：只有一句话）
- 并行时前端同时显示多个专家在思考，各自完成各自消失（现状：只显示最后一个，先完成者清空全部）
- `npm test` 通过；`npm run lint` 无新增类型错误
- 旧入口（@all、onboarding、四个 workflow、Boss 登录后续）行为不变

## 不在本轮范围

- 考公群、考研群接入真 agent
- 专家产出的呈现方式（是否单独成条）
- 删除旧编排代码路径
- 专家跨 turn 的长期记忆（第 5 条只在 turn 内解决）
- 官网投递能力接入主页面（另有设计，暂缓）
