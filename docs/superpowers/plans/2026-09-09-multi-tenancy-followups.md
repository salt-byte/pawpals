# 多租户改造：遗留事项与上线前清单

改造本身已完成（13 个任务，33 个提交，`87e4b9d..b1c3da5`）。本文件记录**没有做**的事，
以及整分支终审给出的两道不同门槛。它是从执行期账本里提炼出来的，账本本身已删除。

## 两道门槛不是一回事

设计稿把「可以合并」和「可以开放注册」分成两件事，终审也照此判断。

### 合并前必须做的——已全部完成

终审列出的五项在最后一轮修复波里都做掉了：插件回报帧丢用户上下文（会崩掉整个进程）、
备份导出给的是别人的数据、每小时备份在多用户下备份零份用户数据、
一批进程级路由对所有登录用户开放、限流键依赖可伪造的 X-Forwarded-For。

### 开放注册前还需要的

1. **额度数字仍未定。** `PAWPALS_DAILY_TOKEN_LIMIT` 不设即无限。设计稿明说这个数必须先定下来。
   现在流式调用终于计入了（此前主聊天路径一个 token 都不记），所以定数之前的实测数据才有意义。
2. **「谁是运维」需要产品决策。** 本轮把改模型/API key、cron、重置计数这些路由在多用户下一律关掉了，
   代价是**包括真正的运维在内**谁都改不了。这是权宜之计，不是设计。
3. **多租户的数据导出与删除完全没有实现。** 导出/恢复两条路由在多用户下已关闭——
   关掉的是一个会把别人简历给你的 bug，不是一个功能。设计稿自己的清单里就有用户自助删除数据这一项。
4. **插件的 reportContext 在多用户下静默 401。** 长期 token 只认 WebSocket，没有 HTTP 通道，
   而 service worker 的跨域 fetch 带不上 cookie。后果是「帮我投递这个岗位」在开着页面时
   本该走的那条识别分支永远不触发。需要决定：给 /api/internal/* 接受 Bearer，还是把这次上报挪到 WebSocket 上。
5. **两条端到端只能人工验。** 两台真实浏览器各装插件、各配一个账号；以及同一用户两台机器
   只有一台执行同一次投递。自动化够不到这两条。
6. `/api/extension/pair` 仍无限流（32^8 空间 + 5 分钟一次性码，暴力不现实，但与 login/register 不对称）。
7. `/api/backup/status` 与 backup_done 广播会把宿主文件系统路径（含操作系统用户名）暴露给每个租户。
   修法要动前端。

## 已知残留（不阻塞，按主题归类）

### 结构与可测性
- `resolveRequestUser` 是整条分支最要害的判定（它回答「这个请求是谁的」），却仍内联在 server.ts 且零测试。
  本轮有三个判定因为「内联即不可测」被抽成纯模块（isAuthExempt、resolveHandshakeUserId、safeUploadPath），
  它们全都在这个判定的下游。现在这组模块是「三个审查员各自反对过的东西的并集」，不是一条设计出来的边界。
- `extension/background/service-worker.js` 零自动化覆盖（它在 import 时就调 chrome.* API，仓库里没有对应脚手架）。
- llm.ts 新增的流式用量拦截逻辑没有单测，验证全靠实测真实 API——而它承载了绝大部分开销。

### 已知的行为妥协
- 五个进程级队列（pendingSearchQueue 等）仍是共享的，只是路由在多用户下被关掉了。
  谁要是重新打开那些路由，跨租户的注入通道会立刻回来——这句话写在闸门处的注释里。
- 队列按 task id 记租约，没有「哪条连接持有」这一维度，所以 A 掉线而 B 在线时 A 的租约要等 B 掉线才回收。
- 用量帧检测取「第一帧带 usage 的」而非最后一帧。当前 provider 只发一次，若将来接入分帧上报累计用量的 provider 会静默少算。
- startServer() 没有 .catch：boot 期同步抛错会变成「进程活着但没在监听」。已确认 listen 之前没有顶层 await，
  故是确定性的启动期失败且启动横幅很响。
- wake_job_session 的额度检查位置比「真会起链」的语义略早，有求职历史的用户在配置了额度时会在连接时多收到一条提示。
- COOKIE_FILE 仍是模块常量。多用户 + Electron 桌面端如果哪天合在一起，A 的 Boss直聘 cookie 会成为 B 的搜索凭据。
  当前云端部署不跑 Electron，故不可达。
- 每小时备份的目录默认在 ~/Documents/PawPals备份，不随 PAWPALS_HOME 走（可用 PAWPALS_BACKUP_DIR 覆盖）。
